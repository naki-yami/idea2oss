# Bug 诊断循环

> 对应手册第 6 步（三）｜ 产出物：最小复现 + 回归测试 +（触发止损线时）一条 ADR 与一张"重新设计 X"的票 ｜ 完成判据：六步都走完，复现从红转绿，回归测试留在仓库里

## 何时用 / 何时不用

**用**：行为不对、报错、间歇性失败、性能回退、只在某些环境下坏；修了一轮没好；别人报了 bug 而你复现不了。

**不用**：一眼定位、一次改好、顺手加了回归测试的——直接走，不必走完六个动作；需求本来就没说清（那是第 2 步的问题，回 `grill-with-ledger`）；已经确认是设计缺陷导致的一整类问题——按设计问题处理，先写 ADR 再开票。

**为什么需要它**：跳过第 2 步直接猜原因，是这类 bug 反复修不好的典型原因。没有一条"能对这个 bug 变红"的复现，你无法判断任何一次改动是真的修好了，还是把症状盖住了。修复循环之所以烧时间，通常不是 bug 太难，而是**没有红过**。

## 输入（开工前必须到手的）

1. 一条可描述的现象：期望什么、实际什么、从什么时候开始（哪个提交、哪次升级之后）。
2. 能复现的运行环境：版本、平台、依赖锁定文件——复现靠它，不靠记忆。
3. 能跑命令的终端，以及读日志/指标的入口。
4. 一份"必须替换掉的值"清单：哪些是密钥、凭据、个人信息（决定第 1 步扫什么）。
5. 当前分支与最近的提交历史（`git log --oneline`，二分要用）。

## 动作

六步，顺序不要跳。每一步都要"做到什么程度算完成"，写在该步最后一行。

1. **脱敏（做在任何输出之前）**
   - 亮出任何命令、终端输出、抓到的产物、截图、issue 正文之前，先把密钥换成 `<REDACTED>`：API key、token、cookie、session、连接串、私钥、webhook 地址、真实邮箱与手机号。
   - 凭证走环境变量（`export TOKEN=...`，或用 `.env` 且 `.env` 在 `.gitignore` 里）。不要写进命令、不要写进测试夹具、不要提交。
   - 贴出去的每一段都按"永久公开"处理。**先脱敏，再贴第一段输出**；顺序反了就只能去轮换密钥。
   - 完成：在要贴的文本里搜一遍 `api[_-]?key|token|secret|password|BEGIN .*PRIVATE KEY`，搜不到真实值。

2. **造反馈回路（先弄出一个"能对这个 bug 变红"的复现）**
   - 目标形状：一条命令 + 一条断言，现在的结果是红。
   - 可以是：失败的单测 / 集成测试、一个最小脚本、一段 curl、一次基准运行（性能回退用固定输入 + 固定次数 + 记录基线数字）。
   - 复现不了就降维度：换更小的输入、关掉并发、固定随机种子、固定时钟与时区、换成本地服务替身、把数据快照下来。
   - 完成：这条回路对**这个** bug 变红，并且在未改动的主干上变绿（主干也红就说明回路搭错了，或 bug 更早就存在——两种都要写清）。跑一次，记住红的样子。

3. **最小化**
   - 删到不能删：去掉无关模块、无关配置、无关数据、无关步骤。
   - 完成：复现脚本不超过一屏；每删掉一项都重新跑过，仍然是红。

4. **假设（把猜测写下来，不要只放在脑子里）**
   - 写 1–3 条候选原因，每条写成"如果它是真的，那么应该观察到 ___ / 不应该出现 ___"。
   - 按"最容易证伪"排序，先打最便宜的那条。
   - 完成：纸上或票据里有一句"我猜是 ___，因为 ___；如果对，应该看到 ___"，且带一个能推翻它的观察。

5. **插桩（验证猜测，不是确认猜测）**
   - 手段：日志、计数器、计时、断点、把中间变量打出来、`git bisect` 二分提交。
   - 一次只改一个变量（一次改五处，等于什么都没验证）。每个观察都回到第 2 步的回路里跑。
   - 要的是"观察到的事实"，不是"看起来像的原因"。假设被推翻就划掉，写下一条——**一条假设被排除也是进展**。
   - 完成：能指着一条输出说"这条证据排除了 A，指向 B"。

6. **修复 + 回归测试**
   - 先让回路变绿，再把回路固化成仓库里的回归测试（进默认测试套件，不是留在你本地的临时脚本）。
   - 验证这条测试真的测到了东西：临时撤销修复，它必须变红。
   - 顺手问一句：同一类错误还有别的地方会犯吗？有就**开票**，不要在同一提交里顺手改到别的模块。
   - 完成：回路绿、全量测试绿、回归测试在无修复的代码上会红；临时插桩已删掉或降级成 debug 级别。

7. **止损线：三轮不收敛就升级成设计问题**
   - 计数口径：每一次"改了代码去跑回路"算一轮；读代码、查文档、想事情不算。
   - 三轮仍未收敛 → **停手**，做两件事：
     1. 写一条 ADR（`docs/adr/NNNN-<短横线标题>.md`）：现状是什么、为什么修不动、代价是什么、判断错了怎么回退。用 `decision-ledger` 把它记进台账。
     2. 另开一张票，标题就是"重新设计 X"，挂到 frontier 上（→ 调用 `ticket-plan`）。
   - 同一条纪律的另一半：同一张票连续两次尝试没有收敛，就回到上一层——重切票、补需求，或者先做原型。
   - 理由：实际项目里烧掉最多时间的往往不是难 bug，而是**不肯认输的修复循环**。"再试一次"是最贵的动作，上下文不会因为多用而变好，只会更贵、更乱。

## 产出物

- 一条最小复现命令（或一个最小测试文件）。
- 一条进仓库的回归测试（默认测试套件会跑到它）。
- 一次修复提交（一次提交只讲一件事，不夹带无关重构）。
- 一段写下来的诊断记录：现象、假设、排除过程、结论（贴在票据里即可，不必单独建文件）。
- 触发止损线时：一条 ADR + 一张"重新设计 X"的票 + 台账里对应的一行。

## 完成判据

- [ ] 贴出去的命令、日志、产物里搜不到真实密钥（全是 `<REDACTED>`）；凭证来自环境变量，仓库里没有 `.env`。
- [ ] 有一条命令能对这个 bug 变红，且我跑过它、看到过红的样子（不是"它应该会红"）。
- [ ] 复现已最小化：不超过一屏，删掉任何一项都会让红消失。
- [ ] 至少写下过一条假设，并且至少有一条假设被证据**排除**（说明插桩在证伪，不是在做确认）。
- [ ] 修复后：复现回路绿，全量测试绿。
- [ ] 回归测试在撤销修复后会红（本地验证过一次）。
- [ ] 修复范围之外发现的问题已开票，没有被夹带进同一个提交。
- [ ] 临时日志、调试开关、打印语句已清理或降级。
- [ ] 若已到第三轮仍不收敛：ADR 已写、重新设计的票已开、本轮修复循环已停止。

## 手工兜底

- **如果装了 `diagnosing-bugs` 这类外部诊断技能，就用它跑这六个动作；没有就按本技能照做。** 六步的全部内容就是上面那六条，不需要任何工具，纸笔也能做（手册第 15 章的兜底路径写的就是"六步照做：脱敏 → 复现 → 最小化 → 假设 → 插桩 → 修复加回归"）。
- **复现不了**：把"复现不了"当成第一手事实写进票据，逐条列出你试过的路径与观察结果；然后改成"先插桩、等它下次出现"——保存输入与现场快照，下次直接重放。先猜原因再修，是这一类 bug 的主要死因。
- **没有测试框架**：写一个脚本，非零退出码代表红。回归测试就是提交前自查清单里、或 CI 里的一条命令。
- **没有可用的 git 历史**（只有一个提交、或历史被压平）：跳过二分，改用手工缩小输入空间，并在结论里写明"未做二分"。
- **只在生产环境能复现**：不要在生产上做实验性修改。先抓现场（输入、日志、指标、数据快照），拿回本地重放。这一条不可省——碰生产凭据要人工批准，最好由你亲手做。
- **性能回退但基线未知**：先补基线（固定输入、固定时长、记录数字），拿到数字再谈优化。没有数字的"变快了"不是结论。

## 下一步

→ 调用 `dual-axis-review`（修完并跑过回归测试后）；触发止损线时 → 调用 `ticket-plan` 开"重新设计 X"的票，并把 ADR 记进 `decision-ledger`。

## 反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 跳过第 2 步直接猜原因 | 没有红灯，任何改动都"看起来像修好了" | 先造出一条能变红的回路 |
| 边贴输出边想着"这个应该没关系" | 密钥一旦贴出去就等同泄露，只能轮换 | 贴之前先替换成 `<REDACTED>` |
| 复现还没红就开始改代码 | 无法判断是修好了还是盖住了 | 先跑一次，看见红 |
| 一次改五个地方再跑 | 不知道是哪一处起作用，失败了也学不到东西 | 一次一个变量 |
| 只找"支持我猜测"的证据 | 确认偏误，容易修到错误的位置 | 每个假设都要有一个能推翻它的观察 |
| 用"再试一次"续命 | 上下文更贵更乱，修复循环吞掉整个会话 | 三轮止损，升级成设计问题 |
| 把临时日志、调试开关留在提交里 | 下一次排障的噪声，也容易被误认成功能 | 收尾清理或降级为 debug |
| 回归测试写成仓库外的脚本 | 没人会再跑它，同一个 bug 会回来 | 进默认测试套件，并验证它会红 |
