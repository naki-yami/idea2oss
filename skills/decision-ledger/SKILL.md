# 决议台账

> 对应手册第 2 步（贯穿第 3/4/6 步）｜ 产出物：`docs/decisions.md` 或 `.scratch/<feature>/ledger.md` ｜ 完成判据：每条决议精确到可验证、都带证据栏、每条都能在实现与验收里找到落点

## 何时用 / 何时不用

**用**：任何一次"这件就这么定了"的谈话之后；写 spec 之前；拆票时给票据标 `Covers:`；第 6 步统计决议追溯率。

**不用**：术语（术语进 `CONTEXT.md`，不是决议）；一次性的临时决定（写进票据的"不做什么"即可）；够格写 ADR 的架构决策——ADR 写全文，台账里留一行指针。

**为什么需要它**：这条流水线上最实质的漏洞是"决议在传递中被压弱"。`CONTEXT.md` 按设计只是术语表，多数决议不够格写 ADR，而第 3 步的 spec 会从对话里重新综合一遍——全程没有任何机制保证已定决议活到最后。精确结论会被压成弱表述：「标签顺序在重启后必须保持不变」变成「persist sessions」，实现只要满足这句弱表述就算完成。**同一次会话里也会发生，不需要上下文过期。** 台账就是给决议加编号，让它每一步都能被回指。

## 输入（开工前必须到手的）

1. 一场已经谈定的对话（或它的记录）。
2. 台账放哪的**一个**决定（见"动作"第 1 步，二选一，不要两处都写）。
3. 已经存在的台账全文（追加，不重写）。

## 动作

1. **定台账位置（项目只选一个）**
   - `.scratch/<feature>/ledger.md`：单人、单 feature、短期。
   - `docs/decisions.md`：打算被人接手或开源时**默认选这个**。理由：编号全局不复用，接手者只读一个文件就能知道全部已定决议。
   - 定了就写进 `AGENTS.md`，别让下一个会话再猜。

2. **建表头**（四列，列名不要改）：

   ```markdown
   | 编号 | 类型 | 决议（精确到可验证） | 证据 |
   | --- | --- | --- | --- |
   | D-01 | 约束 | 标签顺序在重启后保持不变 | 重启后比较顺序 |
   ```

3. **谈定一条就追加一行**——当场写，不攒到最后（清空会话等于全部作废）。

4. **类型只准三种**：
   | 类型 | 含义 | 处理 |
   |---|---|---|
   | 约束 | 不可违背 | 违反即为缺陷，必须开票修 |
   | 默认 | 可改，但要写理由 | 改动时把新理由写进这一行 |
   | 待定 | 还没定 | **必须带一个定下来的期限**；到期未定就升级成第 0 步的问题 |

5. **把决议写"精确到可验证"**。判据是反向的：**能不能写出一条证明它的命令或动作**。
   - ✗ 弱："持久化会话" → ✓ 强："标签顺序在重启后保持不变"（证据：重启后比较顺序）
   - ✗ 弱："错误处理要健壮" → ✓ 强："失败消息可重试，且不清空已有消息与未发送内容"（证据：失败后重试的用例）
   - 写不出证据栏的，说明这条决议还没谈定，标成"待定"并给期限。

6. **编号永不复用**。删掉的决议留一行划掉，不要回收编号——回指一旦指错，台账就失去意义。

7. **三处回指**（台账的价值全在这里）：
   - 第 3 步：spec 的「实现决策」与「测试决策」逐条写 `[D-01]`。落不下去的决议只有两种处理：写进「范围之外」，或说明 spec 漏了它。**两种都比让它悄悄消失好。**
   - 第 4 步：票据头写 `Covers: D-01, D-03`。拆完票检查一次：**台账里每条决议至少被一张票覆盖**——这是唯一能自动发现"决议在拆票时被漏掉"的动作。
   - 第 6 步：规格轴逐条检查"每条决议都能指到实现与验证证据"。

8. **算决议追溯率**：找到证据的决议 ÷ 全部决议。**目标 100%**。低于 100% 只有两种解释：决议被漏了，或被压弱了。指不到证据的，当场开票或写进「范围之外」。

9. **收官前问两句**（很便宜，常常挖出真风险和一次沉默的越权假设）：
   - "还有哪三个问题你没问？"
   - "这轮有哪些结论是你替我决定的？"——替我决定的，逐条进台账。

## 产出物

- 台账文件一份（`docs/decisions.md` 或 `.scratch/<feature>/ledger.md`），四列表格，编号连续、不复用。
- 模板：`templates/ledger.md`（附录 A7 骨架，结构不要改）。
- 回指痕迹：spec 里的 `[D-nn]`、票据头的 `Covers:`、第 6 步的追溯率数字。

## 完成判据

- [ ] 台账位置已定，且**只有一处**；`AGENTS.md` 里写明了它在哪。
- [ ] 每条决议都精确到能写出一条可执行的证据（不是形容词、不是口号）。
- [ ] 每行的「证据」栏非空。
- [ ] 类型只用约束/默认/待定三种；所有"待定"都有期限。
- [ ] 编号连续且无复用。
- [ ] 写 spec 后：每条决议能在 spec 里找到 `[D-nn]`，或明确出现在「范围之外」。
- [ ] 拆票后：每条决议至少被一张票的 `Covers:` 覆盖（`frontier` 非空是 `ticket-plan` 自己的判据，本技能不代管）。
- [ ] 验收前：决议追溯率 = 100%（指不到证据的已开票或已写进「范围之外」）。

## 手工兜底

- 没有 to-spec / to-tickets 这类技能：**台账照样写**。它就是一张四列表格，任何编辑器都能维护；spec 与票据手工写时，正好逐条对照台账（手册给的手写 spec 时间是 30 分钟）。
- 没有 tracker：台账进 `.scratch/<feature>/ledger.md`，回指照写，不影响追溯率统计。
- 对话里谈得太散、找不到决议：只记"改变了后续工作内容"的那些——判断标准是"如果实现时不知道这条，会不会做错"。会 → 记；不会 → 不记。

## 下一步

→ 调用 `write-spec`（把每条决议落到七段文档里，句末带 `[D-nn]`）；拆票时 → 调用 `ticket-plan`。


| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 谈完不记，指望"下一个会话还记得" | 没写下来的共识等于没发生 | 当场追加一行 |
| 决议写成形容词（"要健壮""要快"） | 无法验证，等于没定 | 写成能写出一条证据的句子 |
| 台账放两处（`.scratch` 和 `docs/` 各一份） | 分叉即刻发生，接手者不知道信哪个 | 只留一处，另一处删掉或改成指针 |
| 把术语、待办、想法都塞进台账 | 台账变成流水账，追溯率失去意义 | 术语进 `CONTEXT.md`，任务进票据 |
| 编号复用（删了 D-03 就把新决议编成 D-03） | 旧回指会指到新决议上，追溯全错 | 编号永不复用，划掉保留 |
| 只在 spec 里写决议，不标编号 | 无法自动检查覆盖率 | 句末必须带 `[D-nn]` |
