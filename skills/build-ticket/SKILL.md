# 实行：一票一会话做完一张票

> 对应手册第 5 步 ｜ 产出物：代码 + 测试 + 一个可评审的提交（或分支）｜ 完成判据：测试先红后绿；票据头 `Verify:` 那条命令能跑通；票据里「不做什么」的东西没有顺手做进来

## 何时用 / 何时不用

**用**：手上有一张 `Status: todo` 的票，且票据的验收判据没变；开新会话开工；做完要提交、准备评审。

**不用**：票还没拆 → 先 `ticket-plan`；需求本身有歧义 → 回 `grill-with-ledger` 或 `write-spec` 补一句，不要在实现里替它做决定；票做完了要评审 → `dual-axis-review`；出 bug 修不动 → `bug-diagnosis`。

**一票一会话**：做完一张票就开新会话做下一张。第二张票只读票据文件本身，不继承第一张的中间讨论和踩坑记录——继承上下文等于把上一票的试错背进这一票的预算。

## 输入（开工前必须到手的）

只喂三样东西。其余靠回忆的都是上一个会话的债务。

1. **票据本身**：`.scratch/<feature>/issues/NN-*.md` 或 tracker 上的那张票，头部六行齐全（`Status` / `Blocked by` / `Covers` / `Verify` / `Rounds` / `Sessions`），模板 `templates/ticket.md`。
2. **`CONTEXT.md`**：术语表。实现里用的名字与它一致。
3. **涉及的接口**：这张票要动的 1–2 个接缝，来自 spec 的「实现决策」接缝清单或 `docs/architecture.md`。

开工前先把这张票要读的文件列成一张清单（通常 3–6 个路径），写进票据的 `## Comments`。列不出来的，说明这张票切得不自足——停手回 `ticket-plan`。

## 动作

1. **开新会话，只喂上一步那三样**。不要带上一个会话的讨论、试错与临时结论。把票据改成 `Status: doing`。
2. **复述一遍要做什么**：一句话——这张票做完之后，谁能做什么。与票据「要什么」不一致就停手，先把它说清，不要直接改票。
3. **认接缝，不要新造接缝**：从票据「涉及」里读出接缝；测试挂在这些接缝上，代码内部随便改，测试都不用动。要动的接缝不在票据里 → 停手，按第 11 步处理。没人同意过的接缝会在评审里变成一个发现项。
4. **先红**：写一个测试，跑一次，看它失败。
   - 红这一步同时证明测试真的在测东西。没红过就绿，等于什么都没证明。
   - 一次只加一个测试，加完立刻跑。
5. **再绿**：写最少的实现让它变绿。不要顺手把下一张票的活也写了。
6. **再重构**：内部随便改，测试不动。会因为改内部结构而变红的测试，测的是实现不是行为——改测试。
7. **补边界**：把 spec 用户故事覆盖的出错、边界、空状态、权限面向各补一个用例；失败消息、空输入、超限输入各试一次。
8. **好测试的判据**——拿这张表逐条过：

   | 判据 | 好测试 | 坏测试 |
   |---|---|---|
   | 读起来 | 像一份规格：「用户可以用有效购物车结账」 | 像实现：「`_calc` 被调用两次」 |
   | 断言什么 | 通过公共接口断言行为 | 断言内部结构、私有方法、调用次数 |
   | 重构之后 | 依然成立，不关心内部结构 | 一改内部结构就红 |

9. **跑票据头 `Verify:` 那条命令**，把命令与输出留痕（贴进票据 `## Comments`）。跑不通就是没做完。
10. **一票一提交或一票一分支**，提交信息写「为什么」，不写「改了什么」——改了什么看 diff 更准。例：`fix: 重试时不再清空未发送内容（票 03 / D-02）`。
11. **两次不收敛就上移一层**：同一张票连续两次尝试没收敛，停手，别续命，按三种情况分别处理。

    | 情况 | 处理 |
    |---|---|
    | 票据切得不自足（要读的东西不在票里、要动的接缝太多） | 回 `ticket-plan` 重切 |
    | 需求本身有歧义（两种做法都对，文档没写） | 回 `grill-with-ledger` / `write-spec` 补一句，并往台账追加一行 |
    | 技术不确定（不知道能不能这样做） | 用一次性原型验证，别在主线上做实验 |

12. **收尾自查**：票据「不做什么」里的东西有没有被顺手做进来；有没有留下为过关而凑的 TODO、注释掉的代码、临时开关。有就删掉或开票。
13. **填票据头**：`Rounds:`（这张票尝试了几轮）、`Sessions:`（跨了几个会话）、`Status: review`。`Sessions:` 大于 1 说明票切大了——把原因写进票据，并考虑重切。
14. **守住权限边界**：可以读写代码、跑测试、翻文档；**不可以**碰密钥、生产凭据、force push、重写历史、删数据、发版、改许可证。要做这些，先停下来找人。

## 产出物

- 代码 + 测试：测试挂在事先约定的接缝上，读起来像规格。
- 一个可评审的提交（或一个分支）——第 6 步双轴评审的参照点。
- 更新过的票据头：`Status` / `Rounds` / `Sessions`，以及 `## Comments` 里的 `Verify:` 命令与输出。
- 过程中发现的需求歧义：补进 spec 或台账，或当场开票——不要只在对话里说过。

## 完成判据

- [ ] 测试先红后绿：红那一步有记录（跑了哪条命令、失败输出是什么）。
- [ ] 测试挂在票据「涉及」里事先约定的接缝上，没有新造接缝。
- [ ] 测试读起来像规格，通过公共接口断言行为；改内部结构不会让它变红。
- [ ] spec 用户故事里的出错、边界、空状态面向，各有至少一个用例。
- [ ] 票据头 `Verify:` 那条命令跑通了，命令与输出留痕。
- [ ] 票据「不做什么」里的东西没有被顺手做进来。
- [ ] 一票一提交（或一票一分支）；提交信息写的是「为什么」。
- [ ] 票据头 `Rounds:` / `Sessions:` 填的是真实数字；`Sessions: > 1` 的原因写在票据里。
- [ ] 没有为过关而凑的 TODO、注释掉的代码、临时开关。
- [ ] 没碰密钥 / 生产凭据 / force push / 删数据 / 发版（要做这些已先找人批准）。
- [ ] 开工前列的文件清单在票据里，且实际只读了这些；多读的已补进清单。

## 手工兜底

- 没装 `implement` / `tdd`（外部技能）：**手工红绿**，顺序一步都不省。红：写一个测试、跑一次、看到它失败；绿：写最少实现；再重构。手册的手工路径就是这条。
- 测试框架装不上：先修环境——第 6 步的检测依赖能跑的测试。临时替代是一个最小可执行的验证脚本，但红绿顺序不能省，并要在票据里写明「当前缺什么、怎么补」。
- 提交钩子 / CI 装不上：提交前手工跑一遍 lint、typecheck、test，并按 `templates/manual-review.md` 的标准轴自查。
- `git` 不可用：**无替代，先装**——第 6 步的双轴评审要一个 diff 参照点，没有参照点就没有评审输入。
- 代理完全不可用：人手写也行，判据照走——先红后绿、测试挂约定接缝、`Verify:` 能跑通、提交信息写为什么。

## 反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 写完成代码再补测试 | 「先红」那一步没发生，测试证明不了任何东西 | 先写测试跑一次看它红，再写实现 |
| 测试挂在自己新造的接缝上 | 没人同意过的接缝会在评审里变成一个发现项 | 只挂在票据「涉及」的接缝上；要新造先回第 4 步 |
| 会话边界与票对不上（一个会话做两张票，或一张票跨两个会话） | 前者背着上一票的试错预算；后者靠压缩硬撑，丢掉的正是决议的精度 | 一票一会话；要跨两个会话的票回 `ticket-plan` 重切 |
| 提交信息写「修改了 xx 文件」 | 这句话没有 diff 准 | 写「为什么」，关联票号与 `[D-nn]` |
| 顺手把「不做什么」也做了 | 范围膨胀，交付行为与验收标准矛盾 | 当场开新票，别塞进这张 |
| 两次不收敛还说「再试一次」 | 上下文不会因为多用而变好，只会更贵更乱 | 上移一层：重切票 / 补需求 / 做原型 |
