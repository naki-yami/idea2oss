# 双轴评审与验收

> 对应手册第 6 步 ｜ 产出物：两轴评审报告 + 你本人跑过一遍的结论 ｜ 完成判据：两轴无未决发现项；决议追溯率 100%；票据里有一行 `Accept:`

## 何时用 / 何时不用

**检测分三层，不要把三层混成一个「测试」**——混在一起是质量失控的常见起点。

| 时机 | 用什么 | 在哪一步 |
|---|---|---|
| 写的时候 | 红绿循环（即时检测，不额外开工具） | 内建在 `build-ticket` |
| 改完 | 双轴评审（本技能） | 第 6 步 |
| 出 bug | 六步诊断：脱敏 → 复现 → 最小化 → 假设 → 插桩 → 修复加回归 | → 调用 `bug-diagnosis` |

**用**：一张票实现完（`Status: review`）；交付前；要判断这张票能不能进第 7 步。

**不用**：写代码的过程中（那是 `build-ticket` 的红绿循环）；需求还不确定（回 `grill-with-ledger`，评审挡不住错的需求）；让写代码的那个上下文同时当审查者——审查者要重新读一遍 diff，不继承实现时的判断。

## 输入（开工前必须到手的）

1. **一个固定参照点**，四选一：commit / 分支 / tag / merge-base。**用户不给就问，不要猜。**
2. **票据**（`templates/ticket.md`）：头部有 `Verify:` 行，末尾要有地方写 `Accept:` 行。
3. **spec**：`.scratch/<feature>/spec.md`，规格轴的对照物。
4. **决议台账**：`ledger.md` 或 `docs/decisions.md`，追溯率的分母。
5. **这个仓库自己写下来的规范**：`CONTRIBUTING.md`、`AGENTS.md`、lint / formatter 配置、`docs/` 里的约定。标准轴的对照物是**它**，不是通用品味，也不是你的个人偏好。

## 动作

1. **定参照点**，选法只有两条：

   | 你的工作方式 | 参照点 |
   |---|---|
   | 一票一提交 | 上一个提交（这张票那次提交之前） |
   | 分支开发 | 默认用 merge-base：分支与主干的共同祖先 |

   merge-base 的好处是不会把别人合进来的改动算作你的工作。用户给了参照点就用他给的；没给就问。
2. **先验证参照点**：这个 ref 能不能解析？`git diff <ref>..HEAD` 是不是空的？是空的就先确认参照点，别启动评审。
3. **两轴跑在并行子代理里**，避免互相污染上下文：

   | 轴 | 审什么 | 对照物 | 输出 |
   |---|---|---|---|
   | 标准轴 | 代码是否符合**这个仓库自己写下来的**规范 | `CONTRIBUTING.md` / `AGENTS.md` / lint 配置 / 已有约定 | 发现项 + 位置 + 严重度 |
   | 规格轴 | 代码是否忠实实现了文档的**每一条** | spec 的七段（尤其成功判据与「范围之外」）+ 台账 | 同上 |

4. **两份子代理简报各自写清四件事**：审哪条轴、对照物是谁（给路径）、diff 范围（给 ref）、输出格式（发现项列表，每条带文件与行号）。
5. **两份简报末尾各加一句，原话照抄**：

   > 不要调用 code-review，也不要派发额外代理，直接完成本次评审。

   已知未修 bug：子代理会递归，有报告显示一次跑到 50 个以上代理。无人值守地跑时盯着代理数量，事后检查后台任务列表。
6. **最后并排呈现两份报告，不要合并成一份**。「代码很规范但做错了」和「做对了但代码很脏」是两种不同的结论，合并会把两者都抹掉。
7. **算决议追溯率**：找到证据的决议 ÷ 全部决议。**目标 100%**。低于 100% 只有两种解释：决议被漏了，或被压弱了。指不到证据的，当场开票或写进「范围之外」。
8. **技术验收判据**：两轴都没有未决发现项；有未决项的，每一项必须写成「接受的风险 + 谁接受」（写人名，不写「团队」）。
9. **产品验收你自己做，不能外包**：真跑一遍、真用一遍，回答「这是不是我要的东西」。票据里留一行：

   ```
   Accept: 通过 / 不通过 + 原因
   ```

   技能能告诉你「代码忠实实现了文档的每一条」，不能告诉你「文档本身是不是你要的」。代理验收自己写的代码，等于没验收。
10. **判据必须落成两种可执行物**：一条能跑的命令（`Verify:`）+ 一条人工写下的结论（`Accept:`）。规划得再全也不是门禁（官方 issue #1060）——验收标准、越界禁止项、依赖链都写全了，交付出来的行为仍可能与验收标准矛盾；只写在文档里的判据挡不住任何东西。
11. **隐性欠账当场开票**：任何「以后再说」「下次重构」「先这样」都必须在 tracker 上有一张票，或写进 ADR 明确接受。
12. **填票据头**：`Review:`（两轴发现项计数，指标：评审返工）、`Accept:`、`Status`。验收通过的票才进第 7 步；未通过的留在 frontier 上。

## 产出物

- 两轴评审报告两份（并排呈现），每份带发现项、位置、严重度。
- 票据里：`Accept:` 一行（你亲手跑的结论）、`Review:` 计数、更新后的 `Status`。
- 手工路径：填好的 `templates/manual-review.md`，含结论三行（两轴未决发现项数 + 决议追溯率）。
- 开出的票 / 写进「范围之外」的条目 / 必要的 ADR。
- 修复提交（有发现项时）。

## 完成判据

- [ ] 参照点是明确写下来的一个 ref，且 `git diff <ref>..HEAD` 非空。
- [ ] 标准轴的对照物是**这个仓库自己写下来的**规范；没有成文规范时，报告里明确写了「本仓库无成文规范，按已有约定逐条对比」。
- [ ] 规格轴逐条对了 spec 的成功判据与「范围之外」，不是凭印象。
- [ ] 两份报告并排呈现，没有合并成一份。
- [ ] 两份子代理简报末尾都带了「不要调用 code-review，也不要派发额外代理，直接完成本次评审」。
- [ ] 报告里没有未决发现项；或有未决项，且每项都写了「接受的风险 + 谁接受」，接受者是人。
- [ ] 决议追溯率 = 100%；指不到证据的已开票或已写进「范围之外」。
- [ ] 票据里有一行 `Accept:`，写它的人不是写这段代码的那个代理。
- [ ] `Verify:` 那条命令在这次评审里真的跑过一遍。
- [ ] 「以后再说」的东西全部有票号，没有隐性欠账。
- [ ] 票据头 `Review:` 计数已填。
- [ ] 修复后的回归测试通过；未通过的票没有进第 7 步。

## 手工兜底

- 没有子代理 / 并行能力：两轴**串行**跑，中间清一次上下文。先跑标准轴、写下结论，再开一次跑规格轴——顺序可以换，互相污染不能有。
- 没装 `code-review`（外部技能）：用 `templates/manual-review.md` 逐条过，两轴各六条，末尾的结论三行必须写。
- 评审报告读不回来（太长或被截断）：至少把发现项抄进票据再动手改，别在对话里边聊边改。
- 没有 diff 参照点（git 不可用、或改动没提交）：**无替代**——先提交，或把当前改动存成 patch；没有参照点就没有评审输入。
- 代理完全不可用：你本人按两份清单各过一遍；产品验收照样要亲手跑——这一条本来就不能外包。
- 无人值守环境：盯代理数量，发现递归立即停掉重复的那些。

## 下一步

→ 调用 `session-handoff`（接着走第 7 步交付）；有未决发现项 → 修完回 `build-ticket`；出 bug 且修不动 → 调用 `bug-diagnosis`。

## 反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 把三层检测混成一个「测试」 | 出 bug 时才发现没有反馈回路，改完也没人看过 diff | 写时红绿、改完双轴、出 bug 六步诊断 |
| 两轴合并成一份报告 | 「代码很规范但做错了」被掩盖 | 并排两份，不做合并 |
| 参照点靠猜，或拿 `HEAD` 当参照点 | diff 是空的，或把别人的改动算成你的工作 | 问用户；一票一提交用上一个提交，分支用 merge-base |
| 子代理简报不写反递归那句 | 已知会递归，有报告一次跑到 50+ 代理，烧掉大量 token | 两份简报末尾原话照抄那一句；无人值守时盯代理数 |
| 让代理做产品验收 | 自己判自己，等于没验收 | 你亲手跑一遍并写 `Accept:` |
| 发现项标成「以后再说」，判据只写在文档里 | 欠账会被忘记，没人能追踪；而规划本身不是门禁，交付行为仍可能与验收标准矛盾 | 当场开票或写进 ADR；判据落成一条能跑的命令 + 一条人工结论 |
