# 开源发布与运营

> 对应手册第 8 步（8.1–8.6 + 附录 B）｜ 产出物：LICENSE + README + 社区文件 + CI + 首个 release + CHANGELOG ｜ 完成判据：陌生人 30 分钟测试通过

判据只有一条，但很硬：**陌生人 30 分钟测试**——在一个干净目录里，只读 README，能装起来、跑通一次、并知道要参与该改哪个文件。过不了这一条，"开源"只是把代码放上去了。

## 何时用 / 何时不用

**用**：仓库要给别人用或看之前；打第一个 tag 之前；收到"装不起来""不知道怎么改哪个文件"的反馈时；准备接受外部 PR 时。

**不用**：只自己用的半天小工具——不必补许可证与社区文件，但**密钥与数据边界照旧不能省**；公司内部闭源仓库——可只取 8.4（CI 与分支保护）与 8.5（版本与变更日志）两节。

**顺序不能反**：先过闸（法务与安全），再做门面。门面做得再漂亮，许可证错了要推倒重来。

## 输入（开工前必须到手的）

1. 一段能跑通的代码，以及一条"在别人机器上从零跑起来"的路径（不是"我这能跑"）。
2. 许可证决定：第 0 步定的那一个；没定就先在动作第 1 步定下来。
3. 仓库平台的权限：能改仓库元信息、能设分支保护、能打 tag 与建 release。
4. 依赖清单（`package-lock.json` / `pyproject.toml` / `Cargo.lock` / `go.sum`）。
5. 能搜索仓库历史的权限，用来查密钥（这是要你亲手做的一类动作）。
6. 你打算投入的维护节奏：多久看一次 issue、同时接几件事。

## 动作

1. **先过两道理律闸门**（8.1）
   - **选许可证**：先回答一个问题——你是想让人尽量用，还是想让衍生作品也开源？

     | 你的目标 | 推荐 | 代价 |
     |---|---|---|
     | 想被最广泛使用（含闭源产品） | MIT | 没有专利授权条款 |
     | 同样宽松，但要显式专利授权 | Apache-2.0 | 要求标注你改过哪些文件 |
     | 想让衍生作品也开源 | GPL-3.0 | 传染性，企业政策常直接禁止 |
     | 想让网络服务的改动也开源 | AGPL-3.0 | 覆盖 SaaS，最容易被企业政策挡掉 |

     库偏向宽松许可（MIT / Apache-2.0），用的人越多越好；自托管应用可以更严。
   - **落地三步，三处必须一致**（照 `templates/license-todo.txt` 做）：仓库根目录放 LICENSE 全文；包元数据（`package.json` / `pyproject.toml` / `Cargo.toml`）写 `license` 字段，用标准 SPDX 标识；README 末尾写明许可。平台应能识别出许可证名称而不是 "Unknown"；三处说法不一致、或写 "MIT OR Apache" 这种含糊话，等于没定。
   - **依赖许可兼容**：过一遍直接与间接依赖的许可（`npm ls --all` 配合 license-checker，Python 用 `pip-licenses`），把 GPL / AGPL 与"未知许可"挑出来单独看——一个 GPL / AGPL 依赖会污染你的整体许可。这条检查放进 CI，不靠记忆。
   - **密钥与隐私**：确认仓库历史里没有密钥。**不是删文件，是轮换密钥加清理历史**——已经推出去的密钥默认已泄露，先轮换再清理。示例配置里不放真实凭证（用 `templates/env.example`）；不收集用户数据，收集了就要有隐私说明与删除路径。
   - **第三方素材与 AI 生成内容**：不要把你没有权利的代码、图片、数据集带进来。AI 生成内容的署名与许可规则在不同法域并不一致——**这一条不要外包给代理判断**，要你自己确认，必要时问人。
   - 提醒：一旦有外部贡献者，改许可证需要每一位贡献者同意（除非一开始就有 CLA 或 DCO 约定）。所以许可证在第 0 步就要定。

2. **做门面**（8.2）——README 七段，结构抄 `templates/readme.md`，不要改
   1. **一句话定位**：这是什么，给谁用。
   2. **为什么用它**：与同类项目的差别，说清取舍，不写"更快更强"。
   3. **30 秒上手**：装、跑、看到什么，**三条命令以内**。
   4. **用法示例**：能直接复制粘贴，且真实可用。
   5. **限制与不做什么**：写清楚，能挡掉一半无效 issue。
   6. **现状与路线**：能不能用于生产、下个版本做什么、维护节奏。
   7. **许可与贡献入口**：LICENSE 链接、CONTRIBUTING 链接、issue 入口。
   - **仓库元信息**同样影响发现与信任：`description` 一句话、`topics` 关键词、主页链接、`license` 字段与 LICENSE 文件一致。
   - **徽章只挂你真的在维护的**：CI 状态、最新版本、许可证。**挂着红的 CI 徽章，比不挂更伤。**

3. **补齐社区文件**（8.3）——每个文件回答一个陌生人的问题

   | 文件 | 回答什么问题 | 最小内容（模板） |
   |---|---|---|
   | `README.md` | 这值不值得我看下去 | 七段齐全（`templates/readme.md`） |
   | `LICENSE` | 我能怎么用它 | 选定许可证的全文（`templates/license-todo.txt`） |
   | `CONTRIBUTING.md` | 我怎么参与 | 起环境、跑测试的命令、提交规范、PR 期望（`templates/contributing.md`） |
   | `CODE_OF_CONDUCT.md` | 这里怎么待人 | Contributor Covenant + 联系方式（`templates/code-of-conduct.md`） |
   | `SECURITY.md` | 有漏洞跟谁说 | 私密渠道 + 响应时限 + 支持范围（`templates/security.md`） |
   | issue 模板 | 怎么提问题 | bug：复现步骤/版本/环境；feature：场景/替代方案（`templates/issue-bug.md`、`templates/issue-feature.md`） |
   | PR 模板 | PR 该写什么 | 改了什么 / 为什么 / 怎么验证 / 风险（`templates/pr.md`） |
   | `CODEOWNERS` | 谁必须看一眼 | 维护者与其负责的目录（`templates/CODEOWNERS`） |
   | 标签体系 | 我怎么找活干 | `good first issue` / `help wanted` / `bug` / `enhancement`（`templates/triage-labels.md`） |

   - 标签至少要有四个：`good first issue`、`help wanted`、`bug`、`enhancement`。
   - 完整的内容要求（每个文件的最小内容）见 `references/community-files.md`。
   - **必须最先有的三件：LICENSE、README、SECURITY。** 没许可证的仓库，别人连用都不敢用。

4. **配 CI 与质量门**（8.4，骨架 `templates/ci.yml`、`templates/release.yml`、`templates/dependabot.yml`）
   - **最小流水线**：安装依赖 → lint → typecheck → test → 构建产物。矩阵**只留你真正支持的两个版本**，多一个都是在烧你的时间。
   - **分支保护**：主分支要求 CI 通过、至少一次评审、禁止 force push、禁止直接推主分支。**规则写在平台上，不是写在文档里。**
   - **依赖与安全扫描**：Dependabot 管依赖升级与漏洞告警；CodeQL 或同类工具管代码扫描；Scorecard 可以给仓库做一次安全体检。
   - **发布流水线**：打 tag 触发构建与发布，产物带校验（哈希或签名），让下载的人能验证来源。
   - 判据：**别人提 PR 时 CI 会自动跑，而且失败会挡住合并。** 做不到这两点，等于没有 CI。
   - 细节清单（CI 骨架、分支保护四条、依赖升级、无 CI 平台时的退路）见 `references/ci-and-release.md`。

5. **定版本与变更日志**（8.5，骨架 `templates/changelog.md`）
   - **语义化版本三句话**：主版本号是破坏性变更，次版本号是向后兼容的新功能，补丁号是向后兼容的修复。
   - **判断是否破坏性的三个问题**：有没有人依赖现在这个行为？旧调用会不会报错？数据格式变了吗？任一为"是"，就是主版本。
   - **CHANGELOG 按 Keep a Changelog 六段写**：Added / Changed / Deprecated / Removed / Fixed / Security。它面向使用者，不是 commit 记录的抄写——**同一个功能的三次提交，在日志里是一行**。
   - **每个 release 要有 tag、有说明、有对应的日志段落。** 可以先发 0.x，明确声明接口还会变——这比硬撑 1.0 再破坏一次体面得多。

6. **定运营节奏**（8.6）
   - **issue 分类走状态机**：新 issue → 复现/确认 → 定优先级 → 定归属 → 关闭或转成票。没人管的 issue 会让后来者判断"这个项目死了"。（标签映射见 `templates/triage-labels.md`；本地 tracker 见 `templates/issue-tracker.md`。如果装了 `triage` 这类外部技能就用它；没有就照这条状态机手工走。）
   - **响应节奏**：不承诺 SLA，但要公开"我大概多久看一次"，写进 README 或 CONTRIBUTING。
   - **依赖升级节奏**：每月一次小版本升级，安全告警即时处理；升级必须过 CI——不看日志的升级等于没升。
   - **弃用与归档**：先宣布弃用并给出时间窗口；归档时在 README 顶部写明状态和替代品。
   - **时间预算**：一个人的项目要给"同时接几件事"设上限。这条不是技术问题，是可持续性问题——维护者消失的项目比写得差的项目多得多。

7. **走一遍陌生人 30 分钟测试**（本技能的唯一判据，做法见下）

### 陌生人 30 分钟测试怎么做

三个人为条件，一个都不能松：**干净目录**（不含你的开发环境残留）、**只读 README**（不许翻代码、不许问作者）、**三条命令以内跑通**（装、跑、看到东西）。

逐分钟路径——按这个顺序读，每一步都要有能落脚的文件：

| 分钟 | 找什么 | 落在哪 |
|---|---|---|
| 0–3 | 这是什么、给谁用、值不值得看下去 | README 第一段 + 「为什么用它」 |
| 3–6 | 装起来并跑通一次 | README「30 秒上手」 |
| 6–10 | 里面的词我懂不懂 | `CONTEXT.md`（术语表模板 `templates/CONTEXT.md`） |
| 10–14 | 结构长什么样、该改哪个文件 | `docs/architecture.md`（接缝清单） |
| 14–18 | 为什么当初这么定 | `docs/decisions.md` + `docs/adr/` |
| 18–22 | 下一步要做什么、哪张票可以开工 | 票据 frontier（`.scratch/<feature>/issues/`） |
| 22–26 | 怎么参与、有漏洞跟谁说 | `CONTRIBUTING.md` + `SECURITY.md` |
| 26–30 | 提一个 PR，看 CI 会不会自己跑 | 平台上的 PR 页面 + 分支保护 |

卡在哪一步，就是缺哪一件：

| 卡在 | 缺的东西 |
|---|---|
| 0–3 分钟看不懂它是干什么的 | README 缺「一句话定位」或写成了一堆形容词 |
| 3–6 分钟装不起来 / 报错 | 「30 秒上手」不是真实可用的，或超过三条命令 |
| 6–10 分钟看不懂术语 | 没有 `CONTEXT.md`，或术语表是空的 |
| 10–14 分钟不知道该改哪个文件 | 没有架构文档与接缝清单（回 `ticket-plan` 之前的第 4 步） |
| 14–18 分钟问"为什么这么设计"没人答 | 没有台账 / ADR（回 `decision-ledger`） |
| 18–22 分钟不知道能帮什么 | 没有可开工的票，或没有 `good first issue` |
| 22–26 分钟不知道怎么提、出事找谁 | 缺 CONTRIBUTING / SECURITY |
| 26–30 分钟 PR 上没人管 | 缺 CI 或分支保护（规则没配在平台上） |

做一次要留痕：写下你卡住的分钟数与原因，改完再走一遍。**别自己假装是陌生人**——如果你已经知道答案，就找一个没看过这个仓库的人，或者换台机器、换个目录重来。

## 产出物

- `LICENSE`（全文）+ 包元数据 `license` 字段 + README 许可段（三处一致）。
- `README.md`（七段，`templates/readme.md`）+ 仓库元信息（description / topics / 主页 / license）。
- 社区文件：`CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`、`SECURITY.md`、issue 模板、PR 模板、`CODEOWNERS`、标签体系。
- CI 配置（`templates/ci.yml`）+ 分支保护规则（配在平台上）+ 发布流水线（`templates/release.yml`）+ 依赖告警（`templates/dependabot.yml`）。
- `CHANGELOG.md` + 首个带 tag、带说明的 release。
- 一份陌生人 30 分钟测试记录（卡在哪、改了什么、第二次结果）。

## 完成判据

- [ ] 陌生人 30 分钟测试通过：在干净目录里、只读 README，装起来并跑通一次，且知道要参与该改哪个文件。
- [ ] LICENSE、README、SECURITY 三件齐；LICENSE / 包元数据 / README 三处许可说法完全一致（平台显示的不是 "Unknown"）。
- [ ] 依赖许可清单里没有未处理的 GPL / AGPL / 未知许可依赖，且这条检查在 CI 里有一行。
- [ ] 仓库历史里搜不到密钥；示例配置只有占位符（`templates/env.example`）；如曾有密钥被推出去，已轮换并清理历史。
- [ ] README「30 秒上手」的三条命令，我在一个干净目录里亲手跑过，并写下看到了什么。
- [ ] 徽章只挂了我在维护的（CI / 版本 / 许可证），且 CI 徽章是绿的。
- [ ] 主分支分支保护已开：CI 通过 + 至少一次评审 + 禁止 force push。
- [ ] 用一个测试 PR 验证过：CI 自动跑，且失败会挡住合并。
- [ ] 首个 release 有 tag、有说明、有对应的 CHANGELOG 段落；CHANGELOG 六段结构就位。
- [ ] CONTRIBUTING 里写明了响应节奏（"我大概多久看一次"）和本地要跑的命令。
- [ ] 我用过一次陌生人视角（换目录 / 换机器 / 换人），并留下了卡点记录。

## 手工兜底

- **没有 CI 平台**：至少在 `CONTRIBUTING.md` 里写清本地要跑哪几条命令，并**说明当前没有自动检查**。诚实比假装好；假装有质量门，比承认没有更伤信任。
- **没法配分支保护**（个人账号 / 自建平台）：把"合并前必须 CI 通过、必须有人看过"写成 CONTRIBUTING 里的显式规则，并说明这是靠自觉而非机器——判据因此降级，但要说出来。
- **社区文件来不及补**：可以晚一点补，但 **LICENSE、README、SECURITY 三件必须先有**。Code of Conduct 可以直接用 Contributor Covenant，只填联系方式。
- **没有平台账号（纯本地仓库）**：先按七段写 README、放 LICENSE、写 SECURITY（哪怕只有邮箱），把仓库整理到"随时可以推上去"的状态；等有平台时只做上传与元信息填写。
- **不知道许可证怎么选**：回到那个问题——想让人尽量用，还是想让衍生作品也开源？答不出来就先写 `templates/license-todo.txt` 的内容占位，**别在选之前公开仓库**（无许可证默认保留全部权利，别人不敢用）。
- **依赖许可看不懂**：把导出清单里的许可名逐个查一遍官方说明；碰到不认识的许可，当作"未知许可"处理，不要当成没问题。
- **这仓库根本还跑不起来**（陌生人 3–6 分钟必卡）：回第 5/6 步把代码做实，再回来做门面。README 遮不住跑不起来的代码。

## 下一步

→ 发布之后回到第 0 步：下一个想法的立项，从这里重新开始（→ 调用 `project-brief`）；若第 8 步暴露出流程本身的问题（哪一步总是返工），→ 调用 `flow-tuning`。

## 反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 先做 README 门面，后想许可证 | 许可证错了要推倒重来，门面的功夫全废 | 先过闸，再做门面 |
| 三处许可不一致（或写 "MIT OR Apache"） | 平台显示 Unknown，企业合规直接判"不可用" | LICENSE + 元数据 + README 三处一致 |
| 挂一个红的 CI 徽章 | 比不挂更伤——陌生人看到的是"没人管" | 只挂你真的在维护且是绿的 |
| 分支保护只写在文档里 | 文档不拦人，规则要配在平台上 | 平台设置里配好，并用一个失败 PR 验证 |
| 把 CHANGELOG 写成 commit 日志的抄写 | 使用者看不懂要不要升级 | 同一个功能的三次提交写成一行 |
| 硬撑 1.0 再破坏一次 | 破坏性变更来得没有预告 | 先发 0.x，明确声明接口会变 |
| 在 README 里写"更快更强" | 陌生人无法据此判断，等于没写 | 写清与同类项目的取舍差别 |
| 收集了用户数据却没有隐私与删除路径 | 出事时无法挽回，也过不了合规审查 | 不收集，或写清说明与删除方式 |
| 同时接一堆 issue / PR | 维护者消失的项目比写得差的项目多得多 | 给"同时接几件"设上限，公开响应节奏 |
| 让代理替你确认第三方素材与 AI 生成内容的署名 | 代理的自信与正确之间没有相关性，这是法务判断 | 自己确认，必要时问人 |
