# 技术方案与开发计划

> 对应手册第 4 步 ｜ 产出物：接缝清单 + 票据图 ｜ 完成判据：接缝写下来了，且至少一张票无阻塞、可立刻开工

## 何时用 / 何时不用

**用**：spec 七段齐了，要回答「怎么搭」和「先做哪块」；要给票据标阻塞关系；某个设计问题在对话里争论不出结果（状态机边界、UI 变体、并发时序）。

**不用**：一次会话能做完的活——拷问完直接 → 调用 `build-ticket`，多这一步只是多一次跑偏的机会；需求还没谈定 → 回 `grill-with-ledger`；工程大到 spec 本身都写不出来 → 先 `write-spec`。

**这是两件事，别并成一步**：

| 两件事 | 回答什么 | 产出 |
|---|---|---|
| 技术方案 | 怎么搭 | 模块与接缝清单、必要的 ADR |
| 开发计划 | 先做哪块 | 票据图（票据 + `Blocked by`）、frontier |

## 输入（开工前必须到手的）

1. `.scratch/<feature>/spec.md`（或 tracker 上那份）：七段齐，含成功判据与「范围之外」。模板 `templates/spec.md`。
2. 决议台账：每条决议有编号 `D-nn`（用于票据头的 `Covers:` 与拆票后的覆盖检查）。
3. `CONTEXT.md`：术语表。票据里用的词与它一致，否则下一个会话只能靠猜。
4. tracker 落点：本地 markdown（`.scratch/<feature>/issues/`）或 GitHub / GitLab Issues。没定就先定，别在对话里拆票。
5. 大工程额外要一个落点：`map.md` 的路径。

## 动作

### A. 技术方案：怎么搭

1. **用这套词汇，不要用同义词**——词汇统一了，代理的输出现象级地变短。

   | 词 | 含义 |
   |---|---|
   | 模块 | 任何有接口和实现的东西。尺度无关：一个函数、一个类、一个包都是模块 |
   | 接口 | 外面看进去的那一面 |
   | 深度 | 深模块 = 大量行为藏在一个小接口后面。这是要追求的形状 |
   | 接缝 | 外面看进去只能通过它的那个边界 |
   | 适配器 | 一个适配器是假想的接缝，两个才是真的 |

2. **列模块，判深度**：每个模块一行——名字 / 接口 / 藏在接口后面的是什么。接口和实现一样大的浅模块是坏味道：它会把一张票撕成两张，也会让测试无处可挂。
3. **划接缝，每个接缝一行**：名字 / 通过它的是什么 / 谁调用它。接缝清单直接写进 spec 的「实现决策」一节；内容长就用 `templates/architecture.md` 另存一份并给路径。
4. **接缝与成功判据对得上**：逐条读 spec 的成功判据，问「这条判据要通过哪个接缝才看得见」。指不到接缝的判据，说明方案漏了它。
5. **架构性决策落 ADR**（`templates/adr.md`，写到 `docs/adr/NNNN-*.md`），不要硬塞进产品设计文档——那套模板偏用户故事，对「这个模块的接口该长什么样」是错的形状。spec 里只留一行指针。
6. **争论不出结果就用一次性原型**：造可分享的 HTML，让不懂代码的人也能自己推一遍；它是技术原型，不是产品 UI 设计，用完即弃，结论写进 ADR 或台账。如果装了 `prototype`（外部技能）就用它；没有就手工——最小可跑脚本加一张 ASCII 状态图，同样用完即弃。

### B. 开发计划：先做哪块

7. **按五条拆票，每条都可检查**：

   1. 按用户可见行为切，不按技术层切：「能导出 CSV」是一张票，「写 export 模块」不是。
   2. 一张票一个可验证结果：`Verify:` 写得出具体命令或动作；写不出，说明它还是任务清单。
   3. 一张票要动的接缝不超过两个；超过通常是两张票被写在一起了。
   4. 自检一句：**能不能把这张票交给一个没读过 spec 的新会话做完？** 不能，就是切得不够自足。
   5. 票据头写 `Covers:`，拆完检查一遍：台账里每条决议至少被一张票覆盖。

8. **写票据头六行，结构不要改**（模板 `templates/ticket.md`）：

   ```
   Status: todo
   Blocked by: -            # 无则写 -
   Covers: D-01, D-03       # 覆盖台账里哪些决议
   Verify: <一条命令或动作，能证明这张票做完了>
   Rounds: -                # 尝试了几轮
   Sessions: -              # 跨了几个会话
   ```

   > 口径说明：手册第二章（四）写的是「头部固定五行」，那是修订 1 之前的版本；修订 1 加了 `Covers:`，所以**当前口径是六行**。第 6 步再追加 `Accept:` 与 `Review:` 两行，共八行——这八行就是第十四章六个指标的采集点。

9. **票据是任务图，不是任务清单**：每张票声明它被哪些票阻塞。任何时刻都有一批「没有前置阻塞、可以立刻抓起来做」的票，这批叫 **frontier**。frontier 永远不为空——为空说明依赖成环，或所有票都切大了；你永远该知道下一步抓哪张。
10. **尺寸按一次会话定**：一张票的量级约 100k token。明显撑不满一次会话的可以合并；需要跨两个会话的必须切开，不要靠压缩硬撑——压缩丢掉的正是决议的精度。
11. **工程大到一次会话装不下：先做决策地图**。多一份 `map.md`，票据多一行 `Type: research / prototype / grilling / task`。每张票解决一个决策，不是一块实现。地图完成 = 没有待决事项了，可以交给别人去干。如果装了 `wayfinder`（外部技能）就用它；没有就手工维护 `map.md` 加 `Type:` 行。
12. **落到 tracker 并收尾**：本地模式一票一文件，从 `01` 起编号；评论与历史追加到文件底部的 `## Comments`，不要写进头部。然后摘掉 spec 上的 `ready-for-agent` 标签——按标签轮询的无人值守代理会试图整份实现父级文档，而不是捡票据切片。

## 产出物

- 接缝清单：写进 spec 的「实现决策」一节（每行：名字 / 通过它的是什么 / 谁调用它）；长版另存 `docs/architecture.md`（骨架见 `templates/architecture.md`）。
- 票据图：`.scratch/<feature>/issues/NN-*.md`，或 tracker 上的票据加原生阻塞链接；头部六行齐全。
- 必要的 ADR：`docs/adr/NNNN-*.md`。
- 大工程：`map.md`（决策地图，含 `Type:` 行）。

## 完成判据

- [ ] 每个接缝一行，三个字段（名字 / 通过它的是什么 / 谁调用它）都填了。
- [ ] spec 的每条成功判据都能指到至少一个接缝；指不到的已补进方案或写进「范围之外」。
- [ ] 架构性决策在 ADR 里；spec 的「实现决策」一节里只有指针，没有长论证。
- [ ] 每张票的标题是一个用户可见的结果，不是技术层名词（符合动作第 7 条第 1 款）。
- [ ] 每张票的 `Verify:` 是一条能跑的命令或动作，且来自第 2 步谈定的验收方式，不是拆票时新造的。
- [ ] 每张票要动的接缝 ≤ 2 个。
- [ ] 每张票能交给一个没读过 spec 的新会话（自检问题的答案是「能」，做不到的已重切）。
- [ ] 每张票头部六行齐全：`Status` / `Blocked by` / `Covers` / `Verify` / `Rounds` / `Sessions`。
- [ ] 台账里每条决议至少被一张票的 `Covers:` 覆盖；没被覆盖的已开票或写进「范围之外」。
- [ ] frontier 非空：至少一张票 `Blocked by: -`，你现在就能说出先抓哪张。
- [ ] 没有一张票需要跨两个会话；明显撑不满一次会话的已合并。
- [ ] 大工程：`map.md` 在，每张研究票有 `Type:` 行，地图里没有待决事项。
- [ ] tracker 上 spec 的 `ready-for-agent` 标签已摘掉。

## 手工兜底

- 没装 `to-tickets` / `codebase-design` / `wayfinder` / `prototype`（都是外部技能）：**手工拆完全走得通**。上面五条规则和头部六行本身就是判据，`templates/ticket.md` 复制过去改内容；接缝表用 `templates/architecture.md`。
- tracker 不可用：走本地 markdown 模式（`.scratch/<feature>/issues/NN-*.md`），头部六行照写，阻塞关系写在 `Blocked by:` 里，历史追加到 `## Comments`。
- 接缝谈不下来：用一次性原型做对比，或在 ADR 里记下两个方案与取舍；暂时定不了的标成「待定 + 期限」写进台账。
- 没有 HTML 能力做原型：最小可跑脚本加一张 ASCII 状态图或时序图，结论落进 ADR，同样用完即弃。
- 票据拆不完（拆到第五张还是拆不干净）：说明范围太大——回 `write-spec` 缩范围，或先做决策地图，而不是继续硬拆。

## 下一步

→ 调用 `build-ticket`（从 frontier 上抓一张票，开新会话做）。

## 反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 技术方案与开发计划并成一步 | 「接口该长什么样」和「先做哪块」互相污染，两个都定不下来 | 先 A 后 B：A 出接缝清单，B 出票据图 |
| 按技术层切票（「写 export 模块」），或一张票动三四个接缝 | 每张票都不可验证——做完一堆票也没有用户能用的东西，而且一个会话装不下 | 按用户可见行为切；超过两个接缝就拆成两张票 |
| `Verify:` 写「功能正常」「测试通过」 | 写不出具体命令，说明它还是任务清单 | 写一条能跑的命令或动作 |
| 用同义词换掉这套词汇（组件 / 边界层 / 外面那层） | 每换一个词，代理就多绕一句；接缝跟着对不上 | 模块 / 接口 / 深度 / 接缝 / 适配器，一个都不换 |
| 拆完不做 `Covers:` 覆盖检查 | 决议在拆票这一步被漏掉，到第 6 步算追溯率才发现，那时已晚 | 拆完立刻做一次覆盖检查 |
| 让票据永远停在 `ready-for-agent` | frontier 里堆满已经做完的活，你也不知道下一步抓哪张 | 一票做完手工改 `Status: done` 并写上验证指针 |
