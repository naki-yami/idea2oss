# 产品设计文档（快照，会过期，不要回头改）

> 对应手册第 3 步 ｜ 产出物：`.scratch/<feature>/spec.md`（或 tracker 上的 spec issue）｜ 完成判据：七段齐全、「范围之外」非空、台账每条决议都能找到 `[D-nn]` 回指、文档里没有你不知道的断言

## 何时用 / 何时不用

**它只合成，不问。** 它不做新的访谈，只综合你已经谈定的内容；它不验证任何东西、不决定任何东西——它是已做决策的记录，不是做新决策的地方。官方有一条判据很好用：**文档里断言了你从没说过的东西，那是缺陷。**

**什么时候才值得做**：只有工程大到一次会话装不下时才值得。一次会话能做完的活，在拷问之后直接走第 5 步，**跳过这一步**——官方自己也说「经常你该跳过 spec」。多这一步就是多一次模型跑偏的机会。

**不用**：需求还在谈（先回第 2 步 → 调用 `grill-with-ledger`）；要选技术方案、定接缝（那是第 4 步 → 调用 `ticket-plan`）。

**生命周期四条——这段最反直觉**。没有任何机制保持它同步：它就是「你那一刻知道的东西的快照」，实现第一次教会你新东西，它当场过期。

| 触发 | 做什么 |
|---|---|
| 实现教了你新东西 | **别回头编辑文档**。该长命的是 `CONTEXT.md` 和 ADR；值得留的写进那两个地方（官方明确说「不是去编辑 spec」） |
| 工作交付之后 | 把它当一次性的 |
| 方向变了要转向 | 删掉未完成的票据，保留文档——文档是目的地，票据只是通往目的地的一次性执行步 |
| 目的地本身变了 | 重新走第 2 步和第 3 步，出一份新的 |

**三个已知问题**：

1. **它会被打上 `ready-for-agent` 标签**（意思是「不需要进一步分诊」），按标签轮询的无人值守代理会整份实现它，而不是捡票据切片。跑无人值守之前：拆票后把标签摘掉，或在代理提示词里明确排除父级文档；收尾写明「未经许可不得开始实现」。
2. **超长文档从 tracker 读回时可能被截断**，没有本地副本兜底。修法是上下文卫生：本地留一份 `spec.md` 作为唯一权威副本，**第 3、4 步之间不要清空或压缩上下文**，在同一个窗口跑完。
3. **决议会在这一步被压缩**——它是「从对话再综合一遍」。这就是台账存在的理由（→ 调用 `decision-ledger`）。

## 输入（开工前必须到手的）

1. 第 2 步产物：非空台账 + `CONTEXT.md`（+ 可能有 0 条 ADR）。
2. 那场对话的记录（要能逐句回溯，不能只靠记忆）。
3. 落地位置：`.scratch/<feature>/spec.md` 是**必须**的一份，且在本地。
4. 七段模板：`templates/spec.md`。

## 动作

1. **复制 `templates/spec.md`，结构不要改，只改内容。** 七段的标题原样留着，它们本身就是检查项。
2. **逐段填。做到什么程度算这一段完成**：
   - **1 问题陈述**：谁在什么场景下遇到什么问题；他们现在怎么绕过它。写不出「现在怎么绕过」，说明问题还不够真。
   - **2 解决方案**：一句话说明这个功能做什么，不写实现细节。
   - **3 用户故事**：`作为 <角色>，我要 <能力>，以便 <目的>`。覆盖六个面向——**首次使用 / 重复使用 / 出错 / 边界 / 空状态 / 权限**，逐个点名，**宁可长**。
   - **4 实现决策**：已定的技术选择与理由，句末写 `[D-nn]`；架构性决策写 ADR，这里只放指针。**接缝清单**一行一个：名字 / 通过它的是什么 / 谁调用它。
   - **5 测试决策**：每条成功判据怎么验证、测试挂在哪几个接缝上，句末写 `[D-nn]`。
   - **6 范围之外**：明确不做什么，以及为什么不。**这一节通常是最有用的几行，不许留空。**
   - **7 补充说明**：未决问题、假设、依赖、参考资料。
3. **做台账回指（这一步唯一的机械检查）**：把第 2 步台账里的每条决议逐条落到「实现决策」或「测试决策」并写 `[D-nn]`。落不下去的只有两种处理：它本来就不该进范围（写进「范围之外」），或者说明 spec 漏了它。**两种都比让它悄悄消失好。**
4. **逐句自检「我说过吗」**：每句话问一遍「这是从哪一句对话来的」。指不回去的，删掉，或降级成「补充说明」里的未决问题。写不出验证方式的成功判据，回第 2 步补问，不要在这里猜。
5. **存两处、留权威**：本地 `spec.md` 落盘；发到 tracker 的那份是副本。第 3、4 步在同一个上下文窗口里连着跑完。
6. **做标签卫生**：拆票完成后摘掉 `ready-for-agent`，或在代理提示词里显式排除这份父级文档。

## 产出物

- `.scratch/<feature>/spec.md`（或 tracker spec issue）：七段齐全、句末带 `[D-nn]`。
- 一份非空的「范围之外」清单，每条带「为什么不」。
- 接缝清单（第 4 步拆票直接拿它用）。
- 台账回指痕迹：每条决议的 `[D-nn]`，或在「范围之外」里的显式处置。

## 完成判据

- [ ] 七段都在，标题没有改名、没有合并、没有调序（对照 `templates/spec.md`）。
- [ ] 「范围之外」非空，每条写了「为什么不」。
- [ ] 「用户故事」逐个点名了六个面向：首次使用 / 重复使用 / 出错 / 边界 / 空状态 / 权限（确实不涉及的已写明理由）。
- [ ] 台账里每条决议都能在「实现决策」或「测试决策」找到 `[D-nn]`，或已写进「范围之外」。
- [ ] 「实现决策」的接缝清单一行一个，三列齐全（名字 / 通过它的是什么 / 谁调用它）。
- [ ] 「测试决策」里每条成功判据都有验证方式（命令或动作）。
- [ ] 逐句能做「我从没说过这句吗」的检查：指不回对话的已删除或降级成未决问题。
- [ ] 文档里没有一条断言是你不知道的（读一遍，看到意外就是缺陷——顺便说明拷问太浅，不是文档太长）。
- [ ] 本地 `spec.md` 存在，且是唯一权威副本；第 3、4 步之间没有清空或压缩上下文。
- [ ] 发到 tracker 的那份：拆票后标签已摘掉，或提示词里已排除父级文档。

## 手工兜底

- **没有 to-spec 这类外部技能**：用 `templates/spec.md` 手写，**30 分钟能写完**——手写时正好逐条对照台账，回指反而更不容易漏。如果装了 spec 类技能就用它；没有就按这条手工路径走。
- **tracker 读不回来（文档被截断）**：本地 `spec.md` 就是唯一权威副本，拆票与评审都从本地读，tracker 上那份只当发布物。
- **用户故事凑不齐六个面向**：回第 2 步补一轮拷问（→ 调用 `grill-with-ledger`），不要在文档里编。
- **文档越写越长、越写越像实现方案**：停下来，把技术选择挪到第 4 步的接缝清单里；这一步只管「要什么」，不管「怎么搭」。

## 反模式

| 反模式 | 为什么错 | 改成 |
|---|---|---|
| 让代理「顺便把 spec 写详细点」 | 它会补出你没说过的断言，而你是最后才发现的人 | 只合成，逐句指回对话；指不回去的删掉 |
| 在 spec 里做新决策 | 决策没进台账、没有编号，下游无从回指 | 回第 2 步谈定、进台账，再回填 `[D-nn]` |
| 「范围之外」留空 | 最有用的几行没了，范围会自己膨胀 | 至少写 3 条明确不做的，带理由 |
| 用户故事只写「首次使用」 | 出错 / 边界 / 空状态留到实现时才暴露，返工加倍 | 六个面向逐个点名 |
| 实现教了你新东西就回头改文档 | 它是快照，改它等于维护一份永远追不上的文档 | 写进 `CONTEXT.md` 与 `docs/adr/` |
| 一次会话能做完的活也硬写一份 spec | 多一次模型跑偏的机会，收益为零 | 跳过第 3 步（也不拆票图），直接写一张票开工 → 调用 `build-ticket` |
