# ADR-0003　把结构判据做成可执行体检器，而不是一张文档清单

- **状态**：已接受（2026-09-30）

## 背景

《项目结构与接手标准》列了完整项目该有什么。第一版只有文档：一份 markdown 清单。用它量了四个真实仓库，结果是——定义标准的那份文档自己所在的项目只有 50% 合规，两个真实业务项目 19%。**判据写在文档里，不会自己去执行。** 这是真实权衡：维护一个 28 项的检查器要成本，而它只能覆盖「存在性」，覆盖不了质量。

## 决策

**新增 `tools/check_project.py`：把 28 条机器可判断的判据做成一条命令，有强制项未通过时退出码为 1。**

## 后果

**得到的**：

- 判据从「一句话」变成「一条能跑的命令」，可以直接写进票据的 `Verify:` 或 CI 门禁——这正是源手册第 6 步要求的两种可执行物之一。
- 缺口从「感觉不全」变成「21 项缺失，先补这三件」。
- 反向约束了文档：写不出检查方式的判据，多半本身就不够具体。

**付出的**：

- 28 项检查要随标准演进同步维护；检查器自己也会出错——写它的当天就修了 4 个假阳性/假阴性（`Blocked by: -  # 注释` 被当成阻塞、台账注释里的 `D-03` 被算成真决议、`certifi/cacert.pem` 被报成密钥、`.env.example` 被报成泄漏）。
- 它**只能查存在性与机械一致性**，查不了「测试是不是真挂在接缝上」「文档是不是你要的」。

**判断错了怎么回退**：`check_project.py` 是独立工具，删掉它不影响任何技能——判据清单会留在本文档与 `docs/architecture.md` 里。回退成本接近零，这也是选择「加一个工具」而不是「把检查写进技能正文」的原因。
